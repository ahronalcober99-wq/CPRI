# Notification Delete Design

## Goal

Allow a signed-in user to delete one or all of their in-app notifications from
the navbar dropdown, including a five-second undo window for single deletion.

## Existing model

The MySQL `notifications` table stores UUID IDs (`VARCHAR(36)`), nullable
`userId`, action/title/message/link, nullable `readAt`, and `createdAt`.
Authenticated rows are created for one `userId`; they are not broadcast/shared
rows. Anonymous visitors receive a separate read-only public feed assembled
from announcements and events.

## Backend

Keep the existing `notifications` table and hard-delete only per-user rows.
No schema or migration change is needed. Add authenticated
`DELETE /api/notifications/:id` and `DELETE /api/notifications` routes using
the existing session-based `requireAuth` middleware. Validate a single ID as
a UUID string, then use parameterized SQL constrained by both that ID and
`req.session.userId`. Return `{ ok: true }` for a deletion, 404 when no owned
row matches, and `{ ok: false, message }` with status 500 on server errors.
Clear-all deletes only rows owned by the session user and returns
`{ ok: true, deleted: <count> }`.

The current authenticated list and unread count both query `notifications`
using the session `userId`; hard-deleted rows therefore disappear from both
without additional filters. The anonymous public feed remains read-only.

## Frontend

The shared navbar dropdown is generated by `public/assets/js/main.js` and styled
in `public/assets/css/styles.css`. Render each authenticated notification as a
row wrapper containing a normal navigation link and a sibling delete button;
do not nest the button inside the link. Use Bootstrap Icons. Prevent the button
click from following the row link or invoking mark-read. Reveal the button on
hover-capable devices and keep a compact X affordance visible on touch devices.

Single deletion removes a row optimistically, subtracts one from the unread
badge if it was unread, and shows a dark in-dropdown toast with Undo for five
seconds. Each pending deletion retains its own Undo control if multiple rows
are deleted before their timers expire. Undo before the timer expires cancels
the request, reinserts the original row in its prior position, and restores its
unread count. On timeout, send `DELETE /api/notifications/:id`. If deletion
fails while the page is active, restore the row and badge, then show
“Couldn't delete that notification. Try again.”

Closing the dropdown flushes pending deletions immediately. Leaving the page
also flushes them using credentialed `fetch` with `keepalive: true`. Clear all
uses the existing confirmation dialog with the prompt “Delete all
notifications?” and Cancel/Delete actions, then sends
`DELETE /api/notifications`; on success, clear the list and unread badge. If
there are pending single-delete timers when Clear all is confirmed, cancel
those timers and restore their rows before sending the bulk request. If the
bulk request fails, keep the restored list and show an in-dropdown error. If
the list is empty, show “You're all caught up” and “New notifications will
show up here.”

Use the existing `fetch` wrapper, which maps `/api/...` to the configured API
base and includes session credentials for cross-origin GitHub Pages requests.
Use existing CSS theme variables for dropdown/toast/button surfaces and text.

## Authentication and CORS

`requireAuth` requires `req.session.userId`; client-supplied ownership IDs are
not accepted. The ownership predicate in every delete query includes the
session user ID. Existing CORS preflight allows `DELETE`, echoes requested
headers, and enables credentials for allowed origins.

## Validation

Check route UUID validation and ownership predicates, verify both endpoints
use parameterized statements, and test success/not-found/error responses.
Parse the modified frontend script, verify click propagation and badge/undo
behavior, and check desktop/touch and dark-mode styles. Confirm CORS preflight
allows credentialed DELETE and that no schema SQL is required.
